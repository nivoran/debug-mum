Introduction à UML

1. Qu'est-ce que UML ?

UML signifie Unified Modeling Language (Langage de Modélisation Unifié). C’est un langage graphique utilisé pour représenter, concevoir et documenter les systèmes informatiques.

UML n’est pas un langage de programmation comme PHP, Java ou Python. Il sert plutôt à préparer et organiser le développement d’une application avant d’écrire le code.

Pourquoi utiliser UML ?

  • Visualiser un système
  • Documenter un projet
  • Préparer le développement
  • Faciliter le travail en équipe

1.1 Origine de UML

UML est né dans les années 1990 suite à l’unification de plusieurs méthodes de modélisation orientée objet. Les principaux créateurs sont :

  • Grady Booch
  • James Rumbaugh
  • Ivar Jacobson

Leur objectif était de créer un langage standard compréhensible par tous les développeurs et analystes.

1.2 Relation entre UML et la Programmation Orientée Objet (POO)

UML est fortement lié à la Programmation Orientée Objet (POO). Les concepts utilisés dans UML proviennent directement des notions de la POO :

  • Classe
  • Objet
  • Attribut
  • Méthode
  • Héritage
  • Encapsulation

Ainsi, lorsqu’un développeur crée un diagramme de classes UML, il prépare souvent les futures classes du programme. 

                Classe Etudiant
                -------------------------
                - nom : string
                - email : string
                -------------------------
                + seConnecter()

Cette représentation pourra ensuite être transformée facilement en code PHP, Java ou Python.

1.3 Les particularités de UML

  • Standard international : UML est utilisé dans le monde entier.
  • Graphique : il utilise des diagrammes et des symboles visuels.
  • Indépendant du langage : UML peut être utilisé avec PHP, Java, Python, C#, etc.
  • Orienté objet : il est adapté aux applications modernes basées sur la POO.
  • Facilite la communication : analystes, développeurs et clients peuvent mieux comprendre le projet.
  • Documente le système : UML garde une trace claire de la structure et du fonctionnement du logiciel.

1.4 Pourquoi UML est important ?

Dans les grands projets, développer directement sans plan peut provoquer :

  • des erreurs de conception ;
  • des oublis de fonctionnalités ;
  • des difficultés de maintenance ;
  • une mauvaise communication dans l’équipe.

UML agit donc comme un plan d’architecte avant la construction d’un bâtiment.

1.5 Exemple concret

Avant de développer une application de gestion d’école, on peut utiliser UML pour :

  • identifier les acteurs (étudiant, professeur, admin) ;
  • définir les fonctionnalités ;
  • concevoir les classes ;
  • préparer la base de données ;
  • visualiser les échanges entre objets.

1.6 UML et le Processus Unifié (UP)

UML est souvent utilisé avec une méthode de développement appelée UP (Unified Process) ou Processus Unifié.

Le Processus Unifié est une méthode d’organisation et de gestion des projets informatiques orientés objet. Il guide les développeurs depuis l’analyse des besoins jusqu’au déploiement de l’application.

UML sert principalement d’outil de modélisation dans UP. Autrement dit :

  • UP organise le travail du projet
  • UML permet de représenter graphiquement le système

Les principales phases du Processus Unifié

  • Inception : étude du projet et identification des besoins.
  • Élaboration :analyse détaillée et conception de l’architecture.
  • Construction : développement et programmation de l’application.
  • Transition : livraison et mise en production du système.

Durant toutes ces phases, UML est utilisé pour créer différents diagrammes :

  • diagrammes de cas d’utilisation ;
  • diagrammes de classes ;
  • diagrammes de séquence ;
  • diagrammes d’activités ;
  • etc.

Ainsi, UML et UP sont souvent complémentaires dans les projets de développement logiciel modernes.

2. Les diagrammes UML

Diagrammes structurels

  • Diagramme de classes
  • Diagramme d'objets
  • Diagramme de composants

Diagrammes comportementaux

  • Diagramme de cas d'utilisation
  • Diagramme de séquence

2.1 Diagramme de classes

Le diagramme de classes est l’un des diagrammes les plus importants en UML.

Il permet de représenter la structure d’un système orienté objet.

Ce diagramme décrit :

  • les classes du système ;
  • les attributs ;
  • les méthodes ;
  • les relations entre les classes.

2.1.1 Qu’est-ce qu’une classe ?

Une classe est un modèle permettant de créer des objets.

Elle regroupe :

  • des données → attributs ;
  • des actions → méthodes.

Exemple :

        Classe : Etudiant

Un étudiant réel créé à partir de cette classe sera un objet.

2.1.2 Structure d’une classe UML

Une classe UML est généralement divisée en trois parties :

+----------------------+
|      Etudiant        |
+----------------------+
| - nom : string       |
| - email : string     |
| - age : int          |
+----------------------+
| + seConnecter()      |
| + afficherNotes()    |
+----------------------+

Explication

  • Première partie : nom de la classe.
  • Deuxième partie : attributs.
  • Troisième partie : méthodes.

2.1.3 Les attributs

Les attributs représentent les informations stockées dans l’objet.

Exemple : 

- nom : string
- email : string

Ici :

  • nom est le nom de l’attribut ;
  • string est son type.

2.1.4 Les méthodes

Les méthodes représentent les actions réalisées par l’objet.

Exemple : 

+ seConnecter()
+ afficherNotes()

Ces méthodes indiquent ce que l’objet peut faire.

2.1.5 Visibilité en UML

UML utilise des symboles pour représenter la visibilité.

  • + → public
  • - → privé
  • # → protégé

Exemple : 

- motDePasse : string
+ seConnecter()

2.1.6 Relations entre classes

Les classes peuvent être liées entre elles.

a) Association

Une association représente une relation entre deux classes.

Cela signifie qu’un objet peut être lié à un autre objet.

Exemple :

Un étudiant appartient à une classe. 

Etudiant -------- Classe

Ici :

  • la classe Etudiant est liée à la classe Classe ;
  • chaque étudiant appartient à une classe ;
  • une classe peut contenir plusieurs étudiants.

L’association permet donc de montrer qu’il existe une relation entre les deux classes.

b) Héritage

Une classe peut hériter d’une autre classe. 

Personne
    ▲
    |
Etudiant

Ici, Etudiant hérite de Personne.

c) Composition

Une classe contient fortement une autre classe. 

Voiture ◆-------- Moteur

2.1.7 Exemple concret

Exemple d’un système scolaire : 

+----------------------+
|      Etudiant        |
+----------------------+
| - matricule : string |
| - nom : string       |
+----------------------+
| + afficherNotes()    |
+----------------------+

            |

            |

            v

+----------------------+
|       Classe         |
+----------------------+
| - nomClasse : string |
+----------------------+

2.1.8 Avantages du diagramme de classes

  • préparer le développement ;
  • visualiser la structure du système ;
  • faciliter la programmation orientée objet ;
  • améliorer la maintenance du projet ;
  • servir de documentation technique.

2.1.9 Correspondance avec le code

Le diagramme de classes peut facilement être transformé en code source.

Exemple en PHP : 

class Etudiant {

    private $nom;

    public function afficherNotes(){

    }
}

On retrouve :

  • les attributs ;
  • les méthodes ;
  • la visibilité.

2.2. Diagramme d’objets

Le diagramme d’objets est un diagramme UML qui représente des objets réels à un moment précis de l’exécution du système.

Il peut être considéré comme une “photo instantanée” des objets d’une application.

2.2.1 Différence entre classe et objet

Avant de comprendre le diagramme d’objets, il faut distinguer :

  • la classe ;
  • l’objet.

a) La classe

Une classe est un modèle ou un plan de construction. 

Classe : Etudiant

b) L’objet

Un objet est une instance réelle créée à partir de la classe. 

etudiant1 : Etudiant

Ici :

  • Etudiant = la classe ;
  • etudiant1 = l’objet.

2.2.2 Rôle du diagramme d’objets

Le diagramme d’objets permet de :

  • visualiser les objets existants ;
  • voir les valeurs des attributs ;
  • montrer les relations entre objets ;
  • mieux comprendre le fonctionnement du système.

2.2.3 Structure d’un objet UML

Un objet UML contient généralement :

  • le nom de l’objet ;
  • le nom de la classe ;
  • les valeurs des attributs.

Exemple : 

+----------------------+
| etudiant1 : Etudiant |
+----------------------+
| nom = Rakoto         |
| age = 20             |
+----------------------+

Explication

  • etudiant1 est le nom de l’objet ;
  • Etudiant est la classe ;
  • les attributs possèdent déjà des valeurs réelles.

2.2.4 Relation entre objets

Les objets peuvent être liés entre eux.

Exemple : 

+----------------------+      +------------------------------+
| etudiant1 : Etudiant |----->| classeA : ClasseScolaire    |
+----------------------+      +------------------------------+

Ici :

  • l’objet etudiant1 appartient à classeA ;
  • les deux objets sont liés.

2.2.5 Différence entre diagramme de classes et diagramme d’objets

Diagramme de classes Diagramme d’objets
Représente les modèles Représente les instances réelles
Pas de valeurs réelles Contient des valeurs réelles
Vue générale du système Vue instantanée du système

2.2.6 Exemple concret

Considérons une application scolaire.

Classe UML : 

Classe : Etudiant
- nom
- age

Objets créés : 

+----------------------+
| etudiant1 : Etudiant |
+----------------------+
| nom = Alice          |
| age = 19             |
+----------------------+

+----------------------+
| etudiant2 : Etudiant |
+----------------------+
| nom = Jean           |
| age = 21             |
+----------------------+

2.2.7 Avantages du diagramme d’objets

  • facile à comprendre ;
  • montre des exemples réels ;
  • utile pour les tests et l’analyse ;
  • permet de vérifier les relations entre objets.

2.2.8 Correspondance avec le code

Le diagramme d’objets correspond directement aux objets créés dans le programme.

Exemple en PHP : 

$etudiant1 = new Etudiant();

$etudiant1->nom = "Alice";
$etudiant1->age = 19;

Ici :

  • Etudiant = la classe ;
  • $etudiant1 = l’objet.

2.3 Diagramme de composants

Le diagramme de composants est un diagramme UML utilisé pour représenter l’organisation physique d’une application.

Il montre les différents composants du système ainsi que leurs relations.

Ce diagramme est souvent utilisé dans les projets logiciels importants pour visualiser l’architecture globale.

2.3.1 Qu’est-ce qu’un composant ?

Un composant est une partie du système qui possède un rôle précis.

Il peut s’agir :

  • d’un module ;
  • d’un service ;
  • d’une bibliothèque ;
  • d’un fichier ;
  • d’une API ;
  • d’une base de données.

Chaque composant réalise une tâche spécifique.

2.3.2 Objectif du diagramme de composants

Le diagramme de composants permet de :

  • visualiser l’architecture du logiciel ;
  • montrer la séparation des modules ;
  • comprendre les dépendances ;
  • faciliter la maintenance ;
  • préparer le déploiement de l’application.

2.3.3 Représentation d’un composant

En UML, un composant est représenté par un rectangle spécial. 

+-------------------+
|     Composant     |
|  [ Service Auth ] |
+-------------------+

2.3.4 Exemple simple

Prenons l’exemple d’une application de gestion scolaire.

L’application peut être divisée en plusieurs composants :

  • gestion des étudiants ;
  • gestion des notes ;
  • authentification ;
  • base de données.
+-------------------+
| Authentification  |
+-------------------+
          |
          |
          v
+-------------------+
| Gestion Etudiant  |
+-------------------+
          |
          |
          v
+-------------------+
| Base de Données   |
+-------------------+

Explication

  • le composant Authentification gère les connexions ;
  • le composant Gestion Etudiant gère les étudiants ;
  • ces composants utilisent la base de données.

2.3.5 Dépendance entre composants

Les composants peuvent dépendre les uns des autres.

Cela signifie qu’un composant utilise les services d’un autre composant. 

[Interface Web] -----> [API]

Ici :

  • l’interface web dépend de l’API ;
  • l’API fournit les données nécessaires.

2.3.6 Diagramme de composants et architecture MVC

Le diagramme de composants est très utile pour représenter l’architecture MVC. 

+-------------+
|   Vue       |
+-------------+
       |
       v
+-------------+
| Contrôleur  |
+-------------+
       |
       v
+-------------+
|   Modèle    |
+-------------+

Ici :

  • la Vue affiche les données ;
  • le Contrôleur gère les actions ;
  • le Modèle communique avec la base de données.

2.3.7 Exemple concret avec un site web

Un site e-commerce peut contenir les composants suivants : 

+-------------------+
| Interface Client  |
+-------------------+

+-------------------+
| Gestion Produits  |
+-------------------+

+-------------------+
| Paiement          |
+-------------------+

+-------------------+
| Base de Données   |
+-------------------+

2.3.8 Avantages du diagramme de composants

  • facilite la compréhension du système ;
  • montre l’architecture globale ;
  • améliore l’organisation du projet ;
  • simplifie la maintenance ;
  • utile pour le travail en équipe.

2.3.9 Différence entre diagramme de classes et diagramme de composants

Diagramme de classes Diagramme de composants
Représente les classes Représente les modules du système
Niveau détaillé Niveau architecture
Structure interne Organisation globale

2.3.10 Correspondance avec le développement réel

Dans un vrai projet, les composants peuvent correspondre à :

  • des dossiers ;
  • des microservices ;
  • des APIs ;
  • des bibliothèques ;
  • des modules Laravel ou Symfony.

2.4. Diagramme de cas d’utilisation

Le diagramme de cas d’utilisation (Use Case Diagram) est l’un des diagrammes UML les plus utilisés.

Il permet de représenter les interactions entre les utilisateurs et le système.

Ce diagramme sert principalement à :

  • identifier les fonctionnalités du système ;
  • comprendre les besoins des utilisateurs ;
  • définir les services proposés par l’application ;
  • faciliter la communication avec le client.

2.4.1 Les éléments principaux

a) L’acteur

Un acteur représente une personne ou un élément externe qui interagit avec le système.

L’acteur peut être :

  • un utilisateur ;
  • un administrateur ;
  • un autre système ;
  • une base de données externe.
    Acteur
      |
      |

b) Le cas d’utilisation

Le cas d’utilisation représente une fonctionnalité offerte par le système.

Il est généralement représenté sous forme d’ellipse.

( Se connecter )

c) La relation

Une ligne relie l’acteur au cas d’utilisation pour montrer l’interaction.

Utilisateur ---------> (Connexion)

2.4.2 Exemple simple

Prenons l’exemple d’une application de gestion scolaire.

L’étudiant peut :

  • se connecter ;
  • consulter ses notes ;
  • voir son emploi du temps.
                +----------------------+
                |  Système scolaire    |
                |                      |
Etudiant -----> | (Se connecter)       |
Etudiant -----> | (Consulter notes)    |
Etudiant -----> | (Voir emploi temps)  |
                +----------------------+

2.4.3 Les avantages du diagramme de cas d’utilisation

  • simple à comprendre ;
  • utile pour discuter avec le client ;
  • permet d’identifier les besoins fonctionnels ;
  • sert de base pour les autres diagrammes UML.

2.4.4 Différence entre acteur et utilisateur

Un acteur n’est pas toujours une personne.

Par exemple :

  • un système de paiement ;
  • une API externe ;
  • un serveur de messagerie.

Tous peuvent être considérés comme des acteurs dans UML.

2.4.5 Bonnes pratiques

  • utiliser des noms clairs ;
  • décrire les fonctionnalités importantes ;
  • éviter les diagrammes trop chargés ;
  • bien identifier les acteurs.

2.5. Diagramme de séquence

Le diagramme de séquence est un diagramme UML qui permet de représenter les échanges entre les objets ou les acteurs d’un système.

Il montre :

  • qui communique avec qui ;
  • dans quel ordre ;
  • à quel moment les actions se produisent.

Le diagramme de séquence est très utilisé pour comprendre le fonctionnement dynamique d’une application.

2.5.1 Objectif du diagramme de séquence

Ce diagramme permet de :

  • visualiser le déroulement d’un scénario ;
  • comprendre les interactions du système ;
  • préparer le développement ;
  • identifier les responsabilités des objets.

2.5.2 Les éléments principaux

a) L’acteur

L’acteur représente l’utilisateur ou un système externe. 

Utilisateur

b) L’objet

Les objets participent aux échanges. 

:Authentification
:BaseDeDonnees

c) La ligne de vie

Chaque acteur ou objet possède une ligne verticale appelée ligne de vie.

Elle représente l’existence de l’objet pendant le scénario. 

Utilisateur        :Systeme

     |                 |
     |                 |
     |                 |

d) Les messages

Les messages représentent les échanges entre objets. 

Utilisateur -----> Systeme : login()

Ici, l’utilisateur envoie la commande login() au système.

2.5.3 Fonctionnement du temps

Dans un diagramme de séquence, le temps s’écoule de haut en bas.

Les premières actions apparaissent en haut, puis les suivantes plus bas. 

Action 1
   |
Action 2
   |
Action 3

2.5.4 Exemple simple de connexion

Exemple : un utilisateur se connecte à une application. 

Utilisateur      Systeme      BaseDeDonnees

     |               |               |
     |---- login() ->|               |
     |               |               |
     |               |-- verifier()->|
     |               |               |
     |               |<- resultat ---|
     |               |               |
     |<- succes -----|               |

Explication

  • l’utilisateur envoie une demande de connexion ;
  • le système vérifie les informations ;
  • la base de données répond ;
  • le système renvoie le résultat.

2.5.5 Messages synchrones et asynchrones

a) Message synchrone

L’expéditeur attend une réponse. 

Client -----> Serveur

b) Message asynchrone

L’expéditeur continue sans attendre. 

Client ----->> Service

2.5.6 Activation d’un objet

Dans un diagramme de séquence, un objet peut exécuter une opération pendant un certain temps.

Cette période d’exécution est appelée zone d’activation.

La zone d’activation montre que l’objet est en train de travailler ou de traiter une demande.

Exemple simple

Lorsqu’un utilisateur demande une connexion : 

Utilisateur        Systeme

     |                |
     |-- login() ---->|
     |                |
     |                |==== vérifier utilisateur ====
     |                |
     |<--- succès ----|

Explication

  • l’utilisateur envoie la commande login() ;
  • le système commence alors un traitement ;
  • pendant ce traitement, l’objet est actif ;
  • la partie ==== vérifier utilisateur ==== représente donc la zone d’activation.

Dans les vrais diagrammes UML, cette activation est souvent représentée par un petit rectangle vertical sur la ligne de vie de l’objet.

2.5.7 Exemple dans une application scolaire

Un étudiant consulte ses notes. 

Etudiant        Systeme        BaseDeDonnees

    |               |                 |
    |-- consulter()->|                |
    |               |                 |
    |               |-- rechercher()->|
    |               |                 |
    |               |<- notes --------|
    |               |                 |
    |<- afficher ---|                 |

2.5.8 Avantages du diagramme de séquence

  • facile à comprendre ;
  • montre l’ordre des actions ;
  • utile pour l’analyse fonctionnelle ;
  • prépare la programmation ;
  • facilite la détection des erreurs logiques.

2.5.9 Différence avec le diagramme de classes

Diagramme de classes Diagramme de séquence
Structure du système Fonctionnement du système
Vue statique Vue dynamique
Relations entre classes Échanges entre objets

2.5.10 Correspondance avec le code

Le diagramme de séquence correspond aux appels de méthodes dans le programme.

Exemple en PHP : 

$systeme->login();

$bdd->verifierUtilisateur();

Chaque appel de méthode peut être représenté dans un diagramme de séquence.

2.6 Diagramme d’activités

Le diagramme d’activités est un diagramme UML utilisé pour représenter le déroulement des actions d’un processus.

Il permet de montrer :

  • les différentes étapes d’un traitement ;
  • l’ordre des actions ;
  • les décisions possibles ;
  • les répétitions éventuelles.

Ce diagramme ressemble beaucoup à un organigramme.

2.6.1 Objectif du diagramme d’activités

Le diagramme d’activités permet de :

  • visualiser un processus ;
  • décrire un scénario ;
  • comprendre le fonctionnement du système ;
  • analyser les différentes étapes d’un traitement.

2.6.2 Les éléments principaux

a) Le point de départ

Le diagramme commence généralement par un point de départ. 

●

Il représente le début du processus.

b) Les activités

Une activité représente une action réalisée dans le système. 

[ Saisir mot de passe ]

c) Les transitions

Les flèches montrent l’enchaînement des actions. 

[Connexion] -------> [Vérification]

d) La décision

Une décision permet de représenter plusieurs chemins possibles. 

             /---- Oui ----\
[ Vérifier ]
             \---- Non ----/

e) Le point final

Le point final représente la fin du processus. 

◎

UML est aujourd’hui un outil incontournable dans le développement des applications modernes. Grâce à ses différents diagrammes, il permet de représenter clairement la structure, le fonctionnement et l’organisation d’un système informatique.

Tout au long de ce cours, nous avons découvert :

  • les origines et les objectifs de UML ;
  • sa relation avec la Programmation Orientée Objet ;
  • le Processus Unifié (UP) ;
  • les principaux diagrammes UML ;
  • les outils de modélisation ;
  • la manière de représenter un projet logiciel de façon professionnelle.

UML ne remplace pas la programmation, mais il prépare et organise le travail des développeurs avant le codage. Il joue donc un rôle comparable au plan d’un architecte avant la construction d’un bâtiment.

Une bonne modélisation permet :

  • de mieux comprendre les besoins ;
  • de réduire les erreurs de conception ;
  • de faciliter le travail en équipe ;
  • de produire des applications plus fiables et plus maintenables.

Dans les grands projets informatiques, UML constitue ainsi un véritable langage de communication entre analystes, développeurs, chefs de projets et clients.

La maîtrise de UML représente donc une compétence essentielle pour tout futur développeur, analyste ou ingénieur logiciel.
